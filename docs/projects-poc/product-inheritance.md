# Product inheritance: quotation -> project -> Cin7 Sale -> invoice (no duplicate SKU entry)

**Authoritative source:** the approved quotation. Its sealed baseline now carries `physicalScope` (customer-safe: SKU, description, quantity, unit, product type, package/section origin, selling price; no cost, no margin; internal cost/margin stay in the access-controlled `internalMargin`, whose lines now also carry SKU and quantity). A baseline sealed before this existed is rebuilt identically from its sealed lines.

| Step | What happens | Code |
|---|---|---|
| Quote | single-SKU lines -> `FINISHED_GOOD`; packages with genuine SKUs and known quantities expand once into `DIRECT_COMPONENT` items remembering their package; estimator-priced systems, historic-reference components, unresolved identities and per-metre lines -> one explicit `UNMAPPED` item (never a made-up SKU). Cin7 BOM sub-components are not scope. | `src/newquip/quote/physical-scope.ts` |
| Project | the scope is copied into the project's baseline snapshot with the project (idempotent with project creation; frozen by the DB baseline guard once a claim is approved). Variations enter their products once, at billing start, into their own scope. | `to-project.ts`, `product-scope.ts`, `variation-billing-store.ts` |
| Resolution | an `UNMAPPED` item is resolved only by a manager, with a reason, audited: map to a real Cin7 SKU (verified live, read-only) or exclude from the Sales Order. Only before any claim or Sale exists. | `scope-store.ts`, `resolveScopeItemAction` |
| Cin7 Advanced Sale | lines are derived server-side from the effective scope (one line per SKU, quantities summed, R0); anything unmapped/unresolved fails closed; every SKU is verified live before an intent is stored. Durable intent, idempotency, read-back and reconciliation unchanged. | `cin7-sale-creation-store.ts` |
| Products & Fulfilment | Quoted / Ordered / Assembled / Available / Invoiced / Shipped / Remaining to invoice / Remaining to deliver per SKU, per scope (original + each variation); unknown is `?`, never 0. | `physical-status.ts`, `PhysicalPanel.tsx` |
| Invoice proposal | `Populate Products from Project`: commercial charges separate from R0 lines; default first-dispatch eligibility (shipped - invoiced - reserved); deposit/service claims propose no lines; unreadable evidence proposes nothing; early selection needs a reason (stored on the posting). Recomputed from live Cin7 facts immediately before posting; a rival in-flight posting holding the same units makes this one stand down before anything is sent. | `invoice-proposal.ts`, `invoice-proposal-store.ts`, `cin7-posting-store.ts` |

Not done / still gated: no migration is needed (the register lives in the existing baseline snapshot and the existing `physical_lines` jsonb). Cin7 contracts C1-C10 remain unproven (`cin7-api-contracts-to-verify.md`); the shipped-quantity semantics (C9) in particular decide what "first dispatch" sees. The demonstration quotation NQ-Q-0001 has three unmapped items (M75 system, penning, FORTIS LED) a manager must map or exclude before a Sale can be created.
